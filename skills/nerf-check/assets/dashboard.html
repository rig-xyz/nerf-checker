Sessions you gave up on: moved off —, or started over

Changing model partway through a session is your own verdict on how it was going, and the correction share misses it: frustration builds over a long session rather than showing as one correction. In the latest full week you moved — of — sessions to another model. "Said it struggled" means your first message to the new model called the old one confused, stuck, nerfed or similar; it is a keyword match in English, not a judge. A switch counts in the week of the first prompt on the new model, and moving a small job to a cheaper model counts too. Started over counts sessions of two prompts or more that went quiet for good with a new session opened in the same folder within 15 minutes; "with the same ask" means the new session's first message asked for much the same thing. This is the one place a session abandoned without a word shows up, and it also catches plain task changes, so read it as a tally.

What reviewers found in each model's work

Checks on the code itself, not on your follow-up messages. First CI run passed is the share of pull requests whose checks were all green on the commit the model opened them with, among those that had CI; a red first run counts whatever its cause. Review-bot comments are the bot's inline comments on pull requests the model opened with gh pr create, with the severity the bot gave each one. A recorded review is counted each time the model recorded a pre-push review, and sorted by what its one-line verdict says it surfaced: big (Critical, Major or High), small (Medium, Minor, Low, a nit or an unlabelled finding) or clean. Rechecks are re-marks after a rebase, a merge or a round of fixes, and are left out of the shares. A model with few pull requests or reviews can move a lot from one week to the next.

Did it keep track, and did it check its work?

Re-read counts the model reading lines of a file that were already in its context, with the file not edited in between: a sign it lost track of what it had. Re-read after a compaction counts lines it had read before the conversation was compacted, which is what the compaction cost. Checked its work is the share of prompts where it edited code and then ran a test, a build, a type check, a linter or the code itself before stopping. Rejected is the share of prompts where you turned down a tool call; it stays near zero if you don't approve calls by hand. Weeks stored before these were measured show a dash.

How this was measured, and its limits
  • Only complete weeks are shown. The page is rebuilt from a history kept on your own machine, so it keeps working after Claude Code deletes old transcripts.
  • Source: the Claude Code transcripts on your machine, main threads only. The history keeps numbers per prompt, not the prompt text. Subagents, scheduled runs and SDK sessions are excluded, and duplicated turns from forked sessions are counted once.
  • A prompt is one message you typed, plus everything the model did until your next message. Each prompt carries its model id, effort level, Claude Code version and context size, so trends can be split by them.
  • The judged error share is the main signal. It is a proxy: it counts mistakes you bothered to point out, judged from the last 500 characters of the reply and the first 300 of your answer. The intervals resample whole sessions, since corrections cluster in the sessions that go badly. The judge is a model too: each run has it label a sample twice and the report prints how often the two passes agree, and every label records which judge model and prompt produced it, so a change of judge is flagged rather than read as a change in the model.
  • Keyword counts (apologies, concessions) are cheap but noisy. Thinking tokens come from the API usage field, so they are exact even when thinking text is hidden.
  • What this cannot see: changes in the work itself. Weeks differ in project mix, and harder tasks raise the error share without any change to the model.
  • Review signals: a pull request belongs to the model whose gh pr create call opened it, even if another model pushed later commits. Review-bot comments are read from GitHub at each rebuild; pull requests opened in the last three weeks are read again, older ones keep their last count. Replies and the bot's summary comments are not counted. A recorded review's outcome is read by pattern from the one-line verdict the model wrote, so it is the model's own account of its review.
  • Published trackers measure from the other side, with fixed tasks run on a schedule. This page is one person's real work, which is closer to what you feel but not controlled.
